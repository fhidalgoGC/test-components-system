# blob-interceptor

Documento exclusivo sobre el interceptor `linkConnectorApi` y el soporte para respuestas binarias (Blob), necesario para la descarga de archivos como Excel, PDF, ZIP, imágenes, etc.

---

## Contexto

El interceptor `linkConnectorApi` (`@/interceptors`) está construido sobre `createApiInterceptor` de la librería externa `GC-UI-COMPONENTS`. Centraliza:

- `baseUrl` (`appUrls.URI_LINK_CONNECTOR`)
- `defaultHeaders` (`Content-Type`, `Accept`, `user_id`, `user_name`, `lang`)
- Auth `Bearer` con el token ECC
- Visibilidad de endpoints (`PUBLIC` / `PRIVATE`)
- Headers dinámicos (`addDynamicHeader`)
- Logging y reintentos

Pasar todas las peticiones por este interceptor garantiza consistencia: cualquier cambio de configuración (nuevo header, cambio de baseUrl, refresh de token) se aplica a todos los servicios sin tocarlos uno por uno.

---

## Limitación actual con respuestas binarias

El interceptor parsea la respuesta automáticamente según el `Content-Type`:

```ts
const contentType = response.headers.get('content-type');
if (contentType?.includes('application/json')) {
  data = await response.json();
} else {
  data = await response.text() as unknown as T;
}
```

Solo soporta **JSON** y **texto**. No existe la opción `responseType: 'blob'` (ni `arrayBuffer`). Si se intenta descargar un archivo binario por el interceptor, el body se convierte a string y el archivo queda corrupto al guardarse.

Por eso `downloadJournalFlowExcel` (en `journalFlow.service.ts`) hace `fetch` directo, reutilizando los `defaultHeaders` del interceptor vía `linkConnectorApi.getConfig()` y agregando el `Authorization` y el `Accept` específicos del Excel.

---

## Propuesta de soporte Blob en la librería

Para que **todos** los endpoints (incluidos los binarios) puedan ir por el interceptor, la librería `GC-UI-COMPONENTS` debe agregar una opción `responseType` en `RequestOptions`.

### Cambios sugeridos en `ApiInterceptor.ts`

1. Nuevo tipo y campo opcional:

   ```ts
   export type ResponseType = 'json' | 'text' | 'blob' | 'arrayBuffer';

   export interface RequestOptions {
     // ...campos existentes
     responseType?: ResponseType; // default: auto por content-type
   }
   ```

2. Lectura de la respuesta respetando `responseType`:

   ```ts
   if (options.responseType === 'blob') {
     data = (await response.blob()) as unknown as T;
   } else if (options.responseType === 'arrayBuffer') {
     data = (await response.arrayBuffer()) as unknown as T;
   } else if (options.responseType === 'text') {
     data = (await response.text()) as unknown as T;
   } else if (options.responseType === 'json') {
     data = await response.json();
   } else {
     // comportamiento actual: auto
     const contentType = response.headers.get('content-type');
     if (contentType?.includes('application/json')) {
       data = await response.json();
     } else {
       data = (await response.text()) as unknown as T;
     }
   }
   ```

3. En el manejo de errores: si `responseType` es `'blob'` o `'arrayBuffer'`, **no** intentar `.json()` sobre el body. Usar `response.statusText` como `message`.

4. Propagar `responseType` en los métodos de conveniencia (`get`, `post`, `put`, `delete`):

   ```ts
   get: <T>(
     endpoint: string,
     params?: QueryParams,
     options?: { transform?: ResponseTransformer; responseType?: ResponseType },
   ) =>
     executeRequest<T>(endpoint, {
       method: 'GET',
       params,
       transform: options?.transform,
       responseType: options?.responseType,
     }),
   ```

5. Compatibilidad hacia atrás: el default sigue siendo el comportamiento actual; solo cambia si el consumidor pasa `responseType` explícito.

## Uso esperado en este proyecto (cuando la librería lo soporte)

`downloadJournalFlowExcel` se simplifica a:

```ts
const response = await linkConnectorApi.get<Blob>(
  JOURNAL_FLOW_EXCEL_ENDPOINT,
  query,
  {
    responseType: 'blob',
  },
);

const blob = response.data;
const filename = extractFilenameFromHeader(response.headers['content-disposition'])
  ?? buildExcelFilename(params.startDate, params.endDate);

return { success: true, blob, filename };
```

Con esto desaparece:

- El `fetch` directo.
- La lectura manual de `defaultHeaders`.
- La obtención manual del `Authorization` desde sesión.
- La construcción manual del `URL` con `baseUrl`.

Todo lo gestiona el interceptor.

## Pasos de migración (cuando la librería publique la versión)

1. Actualizar la dependencia en `package.json` a la nueva tag (ej. `github:fhidalgoGC/test-components-system#version.1.3.0`).
2. Reinstalar (`npm install --force`) y reiniciar el dev server.
3. Refactorizar `downloadJournalFlowExcel` según el bloque "Uso esperado".
4. Verificar que el archivo descargado abre correctamente en Excel.
5. Eliminar de `journalFlow.service.ts` la función `getEccTokenFromSession` y la importación de `appUrls` si ya no se usan.
6. Actualizar este documento marcando la migración como completada.
